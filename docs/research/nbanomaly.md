## What is implemented

The README describes ScoutIQ as an NBA player-performance anomaly detector with a FastAPI backend, Next.js frontend, PostgreSQL cache, Isolation Forest, Z-scores, regression-to-mean probabilities, and Gemini-generated scouting reports ([README](https://github.com/Techdude01/NBAnomaly/blob/main/README.md)). The code substantiates the main path:

- `POST /api/players/{nba_id}/analyze` refreshes data, loads cached game logs, requires at least 10 games, runs anomaly detection, and returns the latest 10 games ([players router](https://github.com/Techdude01/NBAnomaly/blob/main/backend/app/routers/players.py)).
- Data ingestion makes direct `requests` calls to `stats.nba.com`, retries with exponential backoff, limits refreshes to 24 hours, and bulk upserts game logs on `(player_id, game_date)` ([NBA data service](https://github.com/Techdude01/NBAnomaly/blob/main/backend/app/services/nba_data.py)). The README’s description of custom browser headers and abandoning `nba_api/PlayerGameLog` is consistent with that implementation.
- Feature engineering includes box-score fields plus approximate usage rate, true shooting, and a simplified Game Score. The code explicitly says usage rate is missing team-level context and Game Score lacks separate offensive/defensive rebounds and fouls ([feature utilities](https://github.com/Techdude01/NBAnomaly/blob/main/backend/app/utils/features.py)).
- The detector standardizes features, fits `IsolationForest(contamination=0.05, random_state=42)`, scores the full player history, and treats the most recent one-game window as anomalous when its prediction is `-1` ([anomaly detector](https://github.com/Techdude01/NBAnomaly/blob/main/backend/app/services/anomaly_detector.py)). It stores the result and reuses it only when the current Z-score JSON exactly matches the existing record.
- Regression probabilities are a heuristic mapping of absolute Z-score to a 1–99% range; the docstring calls it a “rule of thumb.” They are not learned probabilities or calibrated against future games ([anomaly detector](https://github.com/Techdude01/NBAnomaly/blob/main/backend/app/services/anomaly_detector.py)).
- SHAP support is optional and computed for the latest row, but the returned SHAP values are only logged; they are not stored in the `AnomalyResult` constructed by the current detector. The model migration adds a JSON column, so the repository shows an unfinished or recently changed explainability path ([detector](https://github.com/Techdude01/NBAnomaly/blob/main/backend/app/services/anomaly_detector.py), [model](https://github.com/Techdude01/NBAnomaly/blob/main/backend/app/models/player.py), [SHAP migration](https://github.com/Techdude01/NBAnomaly/blob/main/backend/alembic/versions/e2a73c6cce7e_add_shap_values_json_to_anomaly_results.py)).
- Gemini is called only when no cached report exists; the prompt supplies top Z-scores and heuristic regression probabilities, then stores the returned text. If no key is configured, the API returns a setup message ([LLM report service](https://github.com/Techdude01/NBAnomaly/blob/main/backend/app/services/llm_report.py)).

The frontend presents a score gauge, top-stat cards, Z-score chart, cached/generated scouting report, and recent-game table ([dashboard component](https://github.com/Techdude01/NBAnomaly/blob/main/frontend/components/PlayerDashboard.tsx), [gauge](https://github.com/Techdude01/NBAnomaly/blob/main/frontend/components/AnomalyGauge.tsx), [chart](https://github.com/Techdude01/NBAnomaly/blob/main/frontend/components/ZScoreChart.tsx)). The gauge maps the score to a display range of roughly `[-0.3, 0.3]`; this is a presentation transform, not a model calibration ([gauge](https://github.com/Techdude01/NBAnomaly/blob/main/frontend/components/AnomalyGauge.tsx)).

## Operational evidence

The repository includes Docker Compose for PostgreSQL, backend, and frontend, plus a GitHub Actions workflow that installs/lints/builds the frontend, runs backend Ruff checks, and deploys the backend to EC2 on a successful `main` push ([docker-compose.yml](https://github.com/Techdude01/NBAnomaly/blob/main/docker-compose.yml), [CI/CD workflow](https://github.com/Techdude01/NBAnomaly/blob/main/.github/workflows/ci-cd.yml)). The latest visible workflow for commit `e533ba7` completed successfully for both Build & Test and Deploy Backend ([run 22314397002](https://github.com/Techdude01/NBAnomaly/actions/runs/22314397002)); several immediately preceding runs failed, so “CI/CD exists” is supported while broad reliability is not.

The test files are smoke/integration-style scripts: one runs the detector for an existing database record, and another fetches and analyzes ten named players. They print results but contain no assertions, fixture data, accuracy metrics, precision/recall, calibration checks, latency measurements, or reproducible output artifact ([test_ml.py](https://github.com/Techdude01/NBAnomaly/blob/main/backend/test_ml.py), [test_10_players.py](https://github.com/Techdude01/NBAnomaly/blob/main/backend/test_10_players.py)). The public repository therefore provides implementation and deployment evidence, but no measured evidence that anomalies predict subsequent performance or improve scouting decisions.

## Limitations and decisions

The README’s “limit cloud costs,” “limit hallucination,” and “filter typical variance” statements are design goals or claims; the repository does not publish a cost comparison, hallucination evaluation, false-positive/false-negative analysis, or baseline comparison ([README](https://github.com/Techdude01/NBAnomaly/blob/main/README.md)). The current implementation also trains and scores on the same player history, including the latest game, with a fixed contamination setting. That is suitable for a demo signal but leaves leakage and threshold-selection questions for any predictive claim. The latest one-game window is hard-coded at the API boundary, even though the detector accepts a configurable window.

The direct NBA endpoint dependency, browser-header mimicry, and five-season refresh strategy create operational fragility: rate limits, upstream schema changes, and terms-of-service/compliance questions are material risks. PostgreSQL credentials in Compose are development defaults, CORS allows all origins, and the frontend’s public API URL is `http://localhost:8000` in the Compose environment ([Compose](https://github.com/Techdude01/NBAnomaly/blob/main/docker-compose.yml), [FastAPI app](https://github.com/Techdude01/NBAnomaly/blob/main/backend/app/main.py)). These are portfolio-demo trade-offs unless the author can document production hardening.

## Focused questions for the portfolio case study

1. What user decision did the tool need to improve: finding breakouts, buying low, selling high, or prioritizing manual scouting? Which screen or workflow was the primary success criterion?
2. How were `contamination=0.05`, the one-game window, Z-score cutoffs, and regression-probability thresholds selected? Were they tuned on a holdout period or chosen heuristically?
3. Can the author provide a dated evaluation set with a baseline and metrics such as precision/recall by anomaly type, alert lead time, and calibration of the regression probability?
4. What did the ten-player validation actually output, and how many results were anomalous? Are there saved logs or screenshots that can be cited without implying predictive validity?
5. Was the optional SHAP column intentionally left unused, and what explainability result should a user see in the final product?
6. What evidence supports the “limit hallucination” claim, and how was Gemini output reviewed, corrected, or rejected when it conflicted with the statistics?
7. Which deployment and data-source failures were observed in practice, and what production safeguards were added beyond retry/backoff and 24-hour caching?
8. Which decisions were made by Kushal versus inferred from libraries, framework defaults, or the source API? This will keep the portfolio narrative accurate about individual contribution.
